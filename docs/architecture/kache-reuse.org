#+title: Kache reuse evidence

This investigation tests reuse of Kache's existing storage implementation.
It does not add a production cache, an S3 provider, or a second implementation
of Kache's transport. The probe is a root-workspace member with test-only
dependencies; every =mrr-*= dependency inherits the workspace definition.

* Local reuse boundary

=kache-store::ArtifactStore<P>= accepts a caller-owned =ArtifactPolicy=.
The probe supplies a data policy that permits empty blocks, emits no compiler
output kind, and disallows source hardlinks. It calls the existing independent
ingest method, allowing Kache to use copy-on-write clones or copies while
preventing subsequent source mutation from changing stored data.

The adapter supplies the namespace =mrr-data= in the upstream =crate_name=
field, leaves compiler-specific metadata empty, and stores one file named
=block= per entry. This is sufficient for local public-API reuse; it is not
yet a compiler-neutral upstream entry format.

Kache requires 64-character lowercase hexadecimal remote keys. The probe
uses BLAKE3 over the entire CID byte representation as its private lookup key.
It preserves the original MRR CID for verification. Raw and DAG-CBOR CIDs for
the same bytes therefore have separate entries while sharing one upstream
physical blob. Kache's BLAKE3 address does not become a semantic identity.

The executable contracts cover:

- persistence across store reopen;
- codec-distinct entries sharing one physical blob;
- shared-blob lifetime after removal of one referring entry;
- empty content and repeated insertion;
- source mutation isolation;
- rejection or upstream eviction of same-size corrupt content;
- recent-entry protection under size pressure and explicit removal;
- exclusion and release of the same key across two processes.

Two important constraints were found:

1. Durable Kache hits default to metadata-only verification. MRR must continue
   to verify its expected CID after reading the bytes. Kache's configurable
   restore verification is not a replacement for this boundary.
2. =max_size= is a soft eviction target. The initial test expecting immediate
   reclamation failed: Kache protects recently accessed entries for 120 seconds.
   The corrected contract explicitly records this behavior, rather than claiming
   a strict Agent disk-budget guarantee. Age-based reclamation has not been
   measured by this probe.

The helpers are intentionally test-only: reads are whole-block, not bounded
production streaming; no async runtime ownership or automatic download
coalescing is implemented. The lock test proves a usable upstream primitive,
not a completed single-flight read path. The payloads are raw and canonical
DAG-CBOR blocks, not an Arrow/GraphAr query or a complete snapshot round trip.

* Remote reuse boundary

At the pinned upstream revision:

| Owner | Existing capability | Current exposure |
|---+---+---|
| =crates/kache-store= | CAS, index, file isolation, locks, eviction | Public library |
| =src/cache_remote.rs= | =CacheRemote=, =V3Remote=, upload/download entries | Binary-internal module |
| =src/remote_backend.rs= | =RemoteBackend=, OpenDAL S3/filesystem transports, conditional creation | Binary-internal module |
| =src/remote_layout.rs= | Existing v3 tar.zst pack and manifest validation | Binary-internal module |
| =src/remote_resilience.rs= | Deadlines and error classification, plus daemon policy | Mixed transport and application concerns |

The existing remote format uploads a pack and its manifest, rather than one
object per local blob. Local deduplication must not be advertised as remote
cross-entry blob deduplication. A one-block-per-entry strategy may incur
excess object/request overhead; snapshot-sized or bounded batch entries need
measurement before selecting the production unit.

The smallest useful upstream library boundary should expose the existing
=CacheRemote= entry operations and S3/filesystem backend construction. Merely
exporting raw =RemoteBackend= would leave MRR Data to reimplement the pack
format and entry validation, defeating the intended reuse.

Concrete extraction work:

1. Move the remote configuration structs and key-prefix helper out of the
   application-wide configuration owner.
2. Expose the existing backend, download-memory budget, entry layout and entry
   operations in an upstream library. Reuse =kache-format= validators and
   =kache-store= metadata types directly.
3. Separate transport deadlines/error types from service discovery and daemon
   fallback policy in =remote_resilience=.
4. Keep compiler planning, build-manifest prefetch and daemon scheduling in
   the application unless a concrete consumer needs them. Do not copy those
   subsystems into MRR Data or introduce another cache wire format.
5. Add upstream consumer tests for upload from cache A, download into fresh
   cache B, entry registration, corruption, missing objects, interrupted upload,
   and remote acknowledgment. Exercise both filesystem and an S3 endpoint.

* Decision

Prefer reuse of =kache-store= plus extraction of the existing upstream remote
entry API over a new MRR cache engine. Keep MRR-specific CID and snapshot
admission checks in MRR Data. A successful cache upload is not, on its own,
evidence that every child of an MRR snapshot has been published.

* Follow-up: implemented remote extraction

The proposed extraction now exists as an unpublished
[[file:../../tools/kache-remote-probe/kache-remote.patch][upstream patch]], with a
[[file:../../tools/kache-remote-probe/README.md][reproducible consumer workflow]].
It exposes the existing =RemoteLayout= entry operations and backend
construction; the binary retains =CacheRemote= orchestration and prefetch
planning. A clean pinned checkout plus that patch passed the MRR consumer
tests for local-cache/remote recovery, CAR admission, warm-cache reads,
publication failure and CID substitution rejection.

OpenDAL 0.58.2 requires Tokio >=1.52. The root workspace pin was updated from
1.48.0 to 1.53.1, the version in the pinned Kache lockfile. Other pre-existing
dependency versions were preserved except the corresponding Tokio macros.
The actual root workspace passed 72 tests after this update, with one
subprocess helper ignored and invoked by its parent test.

This is filesystem and local S3-wire evidence, not hosted B2/R2 acceptance.
The new library has not been published, and the actual MRR Data product graph
does not yet depend on it. See the workflow's evidence and limitations before
claiming production integration or upstream CI closure.

* MRR content interface

The [[file:content-cache-protocol.org][content cache protocol]] now defines the production
interface boundary independently of the upstream extraction: =ContentStore= for
local adapters, =RemoteContentStore= for remote adapters, and shared verified
read-through/publication operations. Kache continues to own cache mechanisms.
Production adapters now live in =mrr-data-cache=: the pinned Kache store backs
=ContentStore=, and OpenDAL S3 backs =RemoteContentStore=. Local wire tests invoke
these adapters through the shared protocol. The unpublished remote-pack extraction
above remains an independent experiment; it is not required for production use.
