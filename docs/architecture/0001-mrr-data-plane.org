#+title: RFC 0001: MRR Data Plane V1
#+status: proposed
#+options: toc:2
#+property: header-args :eval never-export :exports code

* Status and ownership

This RFC is the canonical design source for =mrr-data=.  It is a proposal, not
a claim that the complete plane is implemented.  The current M0 through M2
executable slices prove relation-specific complete-Fact Arrow and bounded IPC
round trips, canonical snapshot identity, and verified local CARv1 packaging.
Property tests, typed resource-budget failures, malformed corpora, an IPC fuzz
target, and a 512-extra-block content-import scenario guard the import
boundaries.  The upstream
[[https://github.com/tao3k/meta-relational-reasoning][MRR repository]] owns semantic
identity, typed relation schemas and facts, generations, revision bindings,
lineage, queries, transitions, and admission.  This repository owns only their
physical representation, interchange, persistence, and distribution.

The dependency direction is strict:

#+begin_src mermaid
flowchart LR
  S[Source systems]
  M[MRR semantic contracts]
  D[mrr-data physical data plane]
  A[Arrow batches and IPC - default]
  F[DataFusion execution - opt-in]
  G[GraphAr projection - opt-in]
  C[CID blocks and CAR - opt-in]
  O[filesystem or object store]

  S -->|RevisionBinding + admitted facts| M
  M -->|one-way dependency| D
  D --> A
  D --> F
  D --> G
  D --> C
  C --> O
  A -. no semantic authority .-> M
  F -. no semantic authority .-> M
  G -. no semantic authority .-> M
  C -. no semantic authority .-> M
#+end_src

=mrr-data= is not a graph database, query language, reasoning engine, or a
second source of truth.  It must not redefine MRR types and MRR must not import
Arrow, GraphAr, IPLD, CAR, or storage-provider types.

* Design objective

The governing rule is:

#+begin_quote
One semantic relation model, multiple physical forms.
#+end_quote

The same admitted MRR generation may have several equivalent physical
materializations:

- relation-specific Arrow record batches for hot, typed interchange;
- Parquet-backed GraphAr vertex, edge, and adjacency chunks for graph-scale
  persistence and selective IO;
- content-addressed blocks and CAR archives for immutable packaging;
- local filesystem or object-store locations for controlled availability.

The physical forms are caches or durable representations of the semantic
generation.  None can admit a fact, create a generation, or turn Context into
canonical Content.

The performance north star is:

#+begin_quote
Zero-copy when hot, graph-native when large, content-addressed when durable.
#+end_quote

* Calibrated upstream roles

** Apache Arrow

[[https://arrow.apache.org/docs/format/Intro.html][Apache Arrow]] defines a
language-independent columnar memory layout plus IPC protocols.  It is the
canonical /physical interchange/ form in this proposal, not the canonical
semantic truth.  MRR facts and schemas remain authoritative.

V1 uses one relation-specific =RecordBatch= schema per MRR =RelationSchema=.
The user fields preserve declared field order and arity.  Reserved metadata
columns carry at least =FactId=, =GenerationId=, authority, provenance,
completeness, and validity.  A universal
=subject_id/predicate_id/object_id= table is only an optional binary-relation
view; it cannot represent arbitrary typed n-ary relations without loss.

MRR values require an explicit mapping table before implementation:

| MRR value | V1 Arrow requirement |
|-----------+----------------------|
| Entity and typed IDs | canonical typed text under versioned MRR field metadata in the initial slice; a later fixed-width form requires an upstream lossless digest constructor |
| Integer and Boolean | lossless native primitive |
| Decimal and Float | preserve current canonical lexical value; no silent f64 coercion |
| Date, Time, Timestamp | preserve declared units and timezone policy |
| Duration | canonical lexical UTF-8 plus namespaced MRR metadata until MRR defines component semantics |
| ByteString and String | binary and UTF-8 respectively |
| List and Record | declared nested type, never opaque best-effort JSON |
| Null | valid only where the relation schema explicitly permits it |

The current MRR =ValueSchema= already carries decimal precision and scale,
float width, temporal unit and timezone policy, recursive list element shape,
ordered record shape, and field nullability.  The Arrow adapter consumes that
contract directly and returns a typed unsupported-schema error for any mapping
it cannot prove lossless.  Duration remains canonical lexical text in MRR V1;
the adapter must not guess fixed units or calendar semantics from its spelling.

** Apache GraphAr

[[https://graphar.apache.org/docs/specification/format/][Apache GraphAr]] is a
system-independent persistent Property Graph layout.  It describes graph
metadata, chunked vertex and edge tables, property column groups, and
source/destination ordered or unordered adjacency layouts corresponding to
CSR-, CSC-, and COO-style access.  Its payload formats include Parquet and ORC;
Arrow is =mrr-data='s interchange layer, not a GraphAr payload-format claim.

GraphAr is a specialization, not the universal MRR relation model:

- unary entity relations may become vertex labels or properties;
- binary Entity-to-Entity relations may become edges;
- n-ary relations, relations containing non-Entity endpoints, or facts whose
  identity carries independent semantics require an explicit reification
  profile or remain Arrow-only;
- =EntityId= is stored as a stable primary-key property;
- GraphAr internal vertex IDs, row positions, chunk IDs, and adjacency offsets
  are disposable physical identities;
- =FactId= and =RelationId= must survive export, compaction, repartition, and
  import even when every physical identifier changes.

An adapter must reject a relation that has no declared lossless graph
projection.  It must never invent endpoint, label, or property semantics.

** CID, IPLD, and CAR

A CID identifies exact encoded bytes.  It does not establish semantic truth,
authorization, freshness, completeness, or MRR admission.  A semantic
=GenerationId= may have several equivalent physical snapshot roots, and a new
physical layout need not create a new semantic generation.

V1 will define one canonical root-manifest encoding before assigning CIDs.
The normative form should be canonical DAG-CBOR with pinned CID version,
multicodec, and multihash choices.  JSON or YAML may be rendered for humans but
must not become an ambiguous hashing surface.

Arrow IPC bytes are not automatically a semantic canonicalization.  Metadata
ordering, dictionaries, padding, chunking, and writer versions can change the
bytes without changing logical rows.  The V1 codec must pin and test a
deterministic encoding profile or define the CID as physical-artifact identity
only.  It must never claim byte identity is semantic equality.

[[https://ipld.io/specs/transport/car/carv1/][CARv1]] packages a header and
CID-addressed blocks.  CAR is transport packaging, not the snapshot identity:
block order and archive composition may differ while retaining the same root
manifest CID.  Every declared root and referenced child block must be verified
on import.

Content addressing also does not imply IPFS networking.  V1 includes no IPFS
daemon, DHT, gateway, pinning-service, or public-publication dependency.
Default providers are memory and local filesystem; object storage is optional
and policy-controlled.  Public network publication is always an explicit
future capability.

* Four identity layers

The design keeps four layers separate:

| Layer | Examples | Owner |
|-------+----------+-------|
| Semantic identity | =EntityId=, =RelationId=, =FactId=, =GenerationId= | MRR |
| Logical data | =RelationSchema=, typed facts, lineage, query IR | MRR |
| Physical data | Arrow buffers, Parquet files, GraphAr chunks and offsets | mrr-data |
| Content identity | block CID, root manifest CID, CAR roots | mrr-data |

External source revisions use MRR's =ExternalRevisionIdentity= and
=RevisionBinding=.  A Jujutsu =ChangeId= and =CommitId= can populate that typed
provider contract, but JJ is not hard-coded into the core manifest: Git,
databases, object stores, and web sources need the same boundary.

The following equalities are forbidden:

- CID = =GenerationId=;
- GraphAr internal vertex ID = =EntityId=;
- Arrow row position = =FactId=;
- CAR archive bytes = semantic snapshot identity;
- source revision = admitted semantic generation.

* Content Snapshot Manifest V1

The Content root block has the stable schema namespace =mrr.data.snapshot= and
the separate schema version =1=.  A namespace never embeds a version suffix:
namespace selects the owning contract and the numeric version selects one wire
schema within it.  The Content root is never used for a task-scoped Context
projection.  Its CID is computed over the canonical encoded block and is
therefore returned alongside the manifest, not embedded as a self-referential
=root_cid= field.

The logical shape is:

#+begin_src yaml
schema:
  namespace: mrr.data.snapshot
  version: 1
semantic:
  generation_id: "..."
  semantic_snapshot_digest: "..."
  relation_catalog_digest: "..."
  entity_catalog_digest: "..."
source:
  revision_bindings:
    - revision_id: "..."
      provider: "jj | git | database | object-store | web | ..."
      logical_change: "..."
      content_revision: "..."
relations:
  - relation_id: "..."
    arrow_schema:
      namespace: mrr.data.arrow.fact-batch
      version: 1
    row_count: 0
    batches:
      - cid: "..."
        cid_codec: raw
        format: arrow-ipc-file
        row_count: 0
        byte_length: 0
graph_projection:
  schema:
    namespace: mrr.graphar.binary-entity
    version: 1
  graphar_version: "..."
  manifest_cid: "..."
lineage:
  batch_cids: ["..."]
coverage:
  kind: complete | partial | unknown
  declaration_cid: "..."
integrity:
  cid_version: 1
  manifest_codec: dag-cbor
  multihash: sha2-256
#+end_src

=graph_projection= is optional.  A relation descriptor may be Arrow-only.  The
manifest lists each child's CID multicodec separately from its payload format,
and never lists its own CID.  The root itself uses =dag-cbor=; Arrow, GraphAr,
and other opaque child payloads use =raw= unless a registered, frozen codec is
introduced by a later schema version.  Locations, gateway URLs, credentials,
mutable tags, and authorization tokens are outside the immutable root.

The manifest deliberately has no independently invented per-relation semantic
digest or second Arrow-schema digest.  MRR's =RelationCatalogDigest= anchors
the admitted relation semantics.  The frozen Arrow schema namespace
=mrr.data.arrow.fact-batch= at version =1= deterministically projects that
relation schema, and each raw child CID anchors the exact IPC bytes.  A batch
carries its own row count so admission can prove that the relation total equals
the checked sum without opening child payloads.

* Lineage and reasoning bundles

Content addressing is useful at batch and artifact granularity:

- raw evidence batch CID;
- normalized relation batch CID;
- lineage batch CID;
- rule or rule-pack artifact CID;
- candidate result batch CID;
- proof and admission receipt CID;
- root bundle manifest CID.

Semantic granularity and storage-block granularity are deliberately different.
The system does not create one IPLD node per fact or derivation edge by
default.  MRR owns fine-grained =FactId= and =DerivationId= links inside typed
batches; CIDs make those batches and receipts immutable and distributable.

* Query and execution boundary

MRR's =MetaQueryIr= stays storage-neutral but Property-Graph-specific.
=mrr-data-core= now admits a downstream =BoundDataQuery= that pairs it with:

- exact =GenerationId=;
- exact =RelationCatalogDigest= and =EntityCatalogDigest=;
- admitted semantic snapshot digest;
- physical snapshot root CID;
- graph-projection profile and manifest CID when required;
- a physical engine capability profile.

Parsing, schema binding, execution, and semantic admission are separate
receipts.  MRR's =CatalogBoundQuery= is the sole owner of unknown or ambiguous
labels, properties, relation types, and expression typing.  The downstream
binder consumes that admitted receipt and rejects only physical unavailability,
unsupported projection/path modes, stale generations, snapshot drift, or
engine-capability mismatch.  The binder consumes a verified =SnapshotBlock= so
the physical root cannot drift from the manifest it checked.

The physical output bridge preserves that ownership boundary without owning a
second engine lifecycle.  Each engine executes through its native synchronous
or asynchronous API and returns only a =PhysicalQueryOutput= of
storage-neutral columns and rows.  =project_data_query_output= checks the
producer's =DataEngineProfile= against the physical binding, then injects
=QueryResultBinding::for_query= from the immutable =CatalogBoundQuery=.  The
engine cannot supply or replace this identity.  The output remains a
=CandidateQueryResult= until MRR source, lineage, completeness, and transition
owners admit it through =admit_query_result_candidate=.  This protocol is
implemented.  The first opt-in engine adapter lowers the admitted single-hop
binary-Entity slice directly to DataFusion expressions without reparsing SQL.
It owns no async runtime and rejects every undeclared shape before execution;
general query execution remains a later engine-specific milestone.

The native GraphAr contract suite covers the first differential engine slice.
It sends the same admitted binary-Entity facts through an Arrow =RecordBatch=
round trip and the maintained GraphAr write/read path, rebuilds an Arrow batch
from each physical result, and executes both through the same DataFusion plan.
The exact =DataEngineProfile= projection must then produce identical
=CandidateQueryResult= and =QueryResultAdmissionReceipt= values.  This is
evidence for engine and physical-representation parity over the declared
slice, not a general GQL execution claim.

* Content and Context materialization

=mrr-data= may physically store both a canonical Content Graph and a derived
Context Graph, but storage co-location cannot collapse their roles.

- A Content snapshot is source-bound, versioned, provenance-bearing, and
  admitted at a specific MRR generation.
- A Context snapshot is a bounded projection for an actor, task, capability
  scope, selection policy, Content generation, and expiry.
- Every Context root must name the Content =GenerationId= and snapshot root it
  was projected from.  A new Content generation makes freshness a typed
  decision, not a mutable-cache guess.
- Importing, merging, pinning, or querying Context data cannot promote it into
  Content.  It must re-enter through source and MRR admission.

Context therefore has a distinct root schema namespace, =mrr.data.context=,
rather than optional fields inside =mrr.data.snapshot=.  Its immutable
descriptor must contain at least:

#+begin_src yaml
schema:
  namespace: mrr.data.context
  version: 1
content:
  generation_id: "..."
  snapshot_cid: "..."
scope:
  actor_id: "..."
  task_id: "..."
  capability_scope_digest: "..."
  selection_policy_digest: "..."
  expires_at: "..."
projection:
  relations:
    - relation_id: "..."
      arrow_schema:
        namespace: mrr.data.arrow.fact-batch
        version: 1
      cid: "..."
      cid_codec: raw
      format: arrow-ipc-file
integrity:
  cid_version: 1
  manifest_codec: dag-cbor
  multihash: sha2-256
#+end_src

The schema namespace and version pair makes Content and Context roots
non-interchangeable.  Context import additionally checks the named Content
root, actor/task/capability scope, selection policy, and expiry before exposing
projected data.

This is why Content can calibrate and anchor Context without making Arrow,
GraphAr, or a graph database the source of truth.

* Ecosystem placement

The repository boundary follows the wider system ownership:

| Component | Owned responsibility |
|-----------+----------------------|
| MRR | semantic identity, relations, inference candidates, lineage, generations, and admission |
| mrr-data | physical interchange, persistence, immutable packaging, and controlled distribution |
| ASP | source/software evidence and typed provider contracts |
| POO Flow / Marlin | runtime composition, execution policy, ownership, and observability |
| Wendao and other agents | consumers that construct task Context from admitted Content |

A BYODS-style external reasoner may consume an immutable input bundle and
return candidate result and proof bundles.  =mrr-data= can package and identify
those artifacts; MRR decides whether their semantics are admissible, and POO
Flow owns execution.  This repository must not grow a second scheduler,
reasoning engine, or observability framework.

* Security and trust boundary

Import follows a fail-closed ladder:

1. authorize the source and enforce byte, block, row, nesting, and
   decompression budgets;
2. validate CAR framing, roots, duplicate blocks, and referenced-block
   closure;
3. recompute every CID and reject mismatches;
4. validate Arrow/Parquet/GraphAr structures before exposing native buffers;
5. validate the exact MRR schema, IDs, types, cardinality, and generation;
6. run MRR semantic and admission checks.

Apache Arrow explicitly requires validation of untrusted serialized inputs;
malformed offsets, sizes, UTF-8, or extension metadata can otherwise be unsafe.
The V1 bounded importer admits footer, batch, row, recursive-value, and
uncompressed body budgets before materializing arrays.  It rejects dictionary
batches and compressed record bodies until their pre-allocation and
decompression budgets have executable evidence.
V1's trusted in-process interchange is the native =arrow-rs= =RecordBatch=
API.  It does not expose an Arrow C Data or C Stream boundary.  A future ABI
boundary requires a concrete non-Rust consumer, an explicit ownership contract,
and separate executable evidence.  Network or archive input enters through
validated serialized formats.

A matching CID proves only byte integrity.  It does not prove that a payload
is valid Arrow, valid GraphAr, authorized, non-malicious, or admissible MRR
Content.

* API surface

The V1 API follows implemented owners instead of speculative common traits.
The default =mrr-data::arrow= facade exposes relation-specific schema
projection, native =RecordBatch= conversion, and bounded IPC import.  The
opt-in =mrr-data::content= facade exposes the implemented =ContentStore=,
=MemoryContentStore=, =FilesystemContentStore=, and CAR operations.  The
opt-in =mrr-data::graphar= facade exposes the admitted binary-Entity
projection and, only with =graphar-native=, the maintained native writer plus
bounded semantic reader.  The reader reconstructs physical endpoints through
their persisted =EntityId= properties and re-admits complete facts through the
owning MRR relation.

There is no V1 =RelationBatchReader= or =GraphSnapshotStore= abstraction.
Those interfaces would hide materially different Arrow, content, and GraphAr
ownership semantics without an implemented consumer.  A future common trait
requires an owner and a scenario proving that it removes real duplication.
The content store constructs and verifies the CID from the caller-declared
codec and bytes; it must never sniff a payload or silently select a codec.

* Repository shape

Avoid ten speculative crates before there is implementation pressure.  The V1
workspace should begin with:

#+begin_example
mrr-data/
  crates/
    mrr-data/            # public facade; Arrow enabled by default
    mrr-data-profile/    # dependency-light namespaces and numeric versions
    mrr-data-arrow/      # lossless MRR relation <-> Arrow mapping
    mrr-data-core/       # optional manifest admission and snapshot descriptors
    mrr-data-content/    # CID, CAR, memory and filesystem providers
    mrr-data-datafusion/ # opt-in exact-slice physical query execution
    mrr-data-graphar/    # gated Property Graph projection
#+end_example

Object-store, IPLD-model, or provider crates are split only when their API and
dependency boundaries become independently useful.  There is no =mrr-ipfs=
crate in V1.

* Delivery milestones and proof obligations

Milestone numbers record implementation and proof dependencies; they are not a
product-priority ranking.  The active priority is Arrow-first:

1. keep the public facade's default dependency graph limited to Arrow and the
   dependency-light profile crate;
2. close trusted in-process Arrow interchange and its performance evidence;
3. extend opt-in DataFusion execution only through typed, differential slices;
4. close maintained GraphAr writer/read-back evidence for graph-shaped data;
5. maintain manifest and local CID/CAR packaging as an explicit opt-in;
6. defer remote distribution, including IPFS, until a concrete requirement and
   scenario justify it.

** M0: lossless Arrow interchange

Implementation status: the recursive V1 mapping, complete-Fact round trips,
bounded IPC import, property contracts, and fuzz target are implemented.  M0
also provides the public facade's default feature.  Its normal dependency graph
does not import CID, DAG-CBOR, CAR, or GraphAr.  Native projection uses borrowed
values and capacity-sized Arrow builders; reconstruction prepares one typed
decoder tree per batch.  A 10,000-complete-Fact Scenario guards this path
without introducing a C Data or C Stream boundary.  M0 is accepted only after
the current-head CI and review receipts are green; this status does not advance
the later data-plane milestones.

- define every supported MRR value mapping;
- property-test =Fact -> RecordBatch -> Fact=;
- preserve =FactId=, =RelationId=, =GenerationId=, context, field order, and
  canonical values;
- reject unsupported or ambiguous schemas rather than coercing them;
- fuzz untrusted IPC validation.

** M1: identity and manifest

Implementation status: canonical manifest admission, MRR catalog/source
binding, deterministic DAG-CBOR, frozen CID profiles, typed negative contracts,
and a golden root vector are implemented.  This capability is retained behind
the facade's explicit =content= feature; it is not part of the default Arrow
dependency graph.  M1 is accepted only after the current-head CI and review
receipts are green.

- freeze namespace =mrr.data.snapshot= at schema version =1= only after the
  Arrow descriptors have executable round-trip evidence;
- test deterministic root CID across repeated builds;
- reject unknown schema versions, algorithms, codecs, and self-inconsistent
  child descriptors.

** M2: local content-addressed packaging

Implementation status: memory and filesystem stores, upstream CARv1
read/write, full CID/root/referenced-child verification, exact catalog checks,
pre-allocation frame-budget admission, typed import failures,
validation-before-commit, repacking invariance, and the 512-extra-block
performance scenario are implemented.  This local packaging capability is
retained behind the facade's explicit =content= feature; its implementation
status does not make content addressing a current product priority.  M2 is
accepted only after current-head CI and review receipts are green.

- implement memory and filesystem =ContentStore=;
- write/read CAR with full root and child verification;
- prove that repacking CAR does not change the snapshot root;
- enforce import budgets and typed failures;
- demonstrate identical semantic data can have distinct physical CIDs without
  changing =GenerationId=.

** M3: GraphAr specialization

Implementation status: the first admission slice is implemented in
=mrr-data-graphar=.  It admits exactly two ordered, non-null =Entity= fields,
validates every fact through its owning MRR relation, preserves all
semantic identities and context in a physical-ID-free edge record, and rejects
n-ary, nullable-endpoint, scalar-endpoint, and invalid-fact inputs.  A
repartition scenario proves that changing physical grouping does not change
the projected records.  The implemented physical vertex index sorts and
deduplicates that endpoint set, assigns dense GraphAr-local =i64= identifiers,
and retains a bidirectional mapping.  Its result is invariant under edge input
order.  Internal IDs remain disposable: the native writer must persist the
semantic =EntityId= as a property and import must restore it from that property.

The crate intentionally does not encode GraphAr YAML, Parquet, chunk IDs, or
adjacency tables.  The maintained =graphar-rs= binding is an in-tree CXX
binding that compiles the Apache GraphAr C++ implementation and requires Arrow
C++ development libraries; the unrelated crates.io package named =graphar= is
not used.  It exposes the edge writer and bounded high-level collection reader
needed by the admitted profile, so MRR Data composes the native API instead of
introducing a second private GraphAr wire implementation.

The Apache proposal for the edge-writer binding is recorded by
[[https://github.com/apache/incubator-graphar/issues/976][GraphAr issue #976]]
and [[https://github.com/apache/incubator-graphar/pull/977][PR #977]].  The PR
was closed intentionally: =GTrunSec/incubator-graphar= is the maintained source
for this extension, and an Apache merge is not a current release gate.  Apache
=main= remains a compatibility and synchronization baseline.  The reader is
implemented and admitted in the same maintained fork rather than as a private
reader in MRR Data.

The =native-graphar= Cargo feature pins the immutable maintained fork commit
=4d4b29715d9825bd3e9b78589cfb863880b9d1d8= and exercises the native Rust/C++
writer and reader.  The adapter writes semantic =EntityId= vertex
properties plus relation identity and full MRR context on every edge, stages a
complete dataset, then renames it into place.  Its bounded semantic reader
exports the upstream Arrow tables through the Arrow C Stream interface and
borrows their buffers in Rust rather than rebuilding owned string rows.  It
resolves physical endpoints through the vertex table, parses every identity
and context discriminator into its MRR V1 type, reconstructs =Fact= values,
and re-admits each result through =BinaryEntityProjection=.  Duplicate facts,
unknown physical endpoints, ambiguous vertex identities, foreign projections,
malformed contexts, and row-budget overflow fail closed.  Admission requires
an immutable fork revision, owner-maintained tests, and Linux/macOS native CI;
it does not depend on Apache review.  Native CI remains separate so ordinary
Rust feedback does not inherit the C++ build latency.  An isolated fixed
10,000-edge Scenario uses two warmups and 41 measured samples, alternating
ABBA and BAAB execution order over the identical eleven-property projection.
It rejects the maintained native Parquet path unless its median paired sample
is at least five percent faster than the official GraphAr read, retains
P50/P95/P99/max distributions for diagnosis, and independently rejects Arrow
C Stream import above =min(1ms, 10% of official P95)=.  Semantic read keeps
P50 below =300ms= and P95 below =500ms=; prepared semantic admission keeps P50
below =25ms= and P95 below =50ms=.  The committed local reference receipt
records official P50 =9.76ms=, native P50 =8.35ms=, Arrow C Stream import P95
=0.18ms=, and complete parity-scenario P95 =228.05ms=.  These observations are
evidence for this revision and host only, not universal throughput claims.

- implement only the declared binary-Entity projection first;
- preserve canonical IDs through repartition and compaction;
- reject n-ary and unsupported value shapes unless a versioned reification
  profile exists;
- run differential read scenarios against the maintained GraphAr implementation.

** M4: controlled distribution

- add an object-store provider behind the same =ContentStore= contract;
- keep locations and credentials outside immutable manifests;
- measure selective column and adjacency reads without shrinking the corpus;
- consider private IPFS transport only after evidence shows a requirement not
  met by CAR plus object storage.

Every milestone needs positive round trips, typed negative contracts,
determinism receipts, and performance scenarios.  A passing parser, a matching
CID, or a readable GraphAr dataset alone is not semantic closure.

* Non-goals for V1

- implementing a graph database or query optimizer;
- replacing MRR identity, lineage, query, or admission types;
- universal RDF/triple normalization of n-ary relations;
- equating physical and semantic identity;
- public IPFS publication, gateway fallback, or ambient network discovery;
- silent compatibility modes for unsupported schemas;
- claiming GraphAr or Arrow integration before round-trip gates pass.
