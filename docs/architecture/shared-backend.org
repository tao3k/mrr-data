#+TITLE: Shared Production Backend: implementation and qualification
#+DATE: 2026-10-03

* Ownership and dependency direction

[[file:../../crates/mrr-data-backend/src/lib.rs][mrr-data-backend]] is one engine with provider modules/features. It has no
Cedar, Commerce, Example or application-runtime dependency. All Production
Profiles/Cases can consume its content transaction contract. Domain adapters
supply validation; Cases select provider/configuration. MRR Data owns physical
persistence; MRR owns semantic admission; the Host/POO Flow owns the runtime.

The architecture is synchronized with Cedar Production design at
[[https://github.com/tao3k/cedar-poo-spec/blob/bcacabbdd188a821799dc6be92ebbed4a7c46214/Productions/Backend.org][the immutable Production backend design]]. MRR Commerce now pins that Cedar revision.
No reverse Cedar-to-MRR dependency was introduced. Updating a profile/schema
version must not create a fresh coordination home for pending/spent authority;
canonical registry enrollment and migration remain Host responsibilities.

* Implemented common engine

- Explicit async opening borrows a Host Tokio Handle. Constructors perform no I/O.
  Opening/recovery complete before a Ready handle is exposed. No process signal
  handlers or extra runtime are created.
- Profile plus deployment namespace plus scope form a parameterized tuple key.
  Operation identity binds the exact expected revision/CID and replacement CID.
  Caller IDs are bounded before copying or enqueueing. Admission charges fixed
  overhead plus eight times the total identity bytes for owned strings/JSON escapes;
  cache diagnostic payloads are not copied into the metadata worker. This is a
  request budget, not a bound on the process allocator/runtime/database cache.
- One atomic admission lock covers lifecycle and worker leases. Fresh writes have
  count/byte limits; recovery has a separate count and 16 KiB reservation per slot.
  Saturation is a known no-write refusal. There is no unbounded retry queue.
- Blocking provider work runs on spawn_blocking. Once admitted, the backend owns
  its lease and completion even if the caller cancels. Worker loss after submission
  is Unknown. A rejected/canceled validator before write performs no new commit.
- Validators run only for Apply while the metadata transaction is protected.
  Exact replay skips validation and returns historical status, including after
  the head advanced. This result is never a payment/send capability.
- Shutdown seals all fresh entrypoints, drains accepted writes and recovery,
  then closes provider handles. A canceled shutdown waiter leaves the owned drain
  task alive. Repeated/concurrent calls share the cached terminal report.
  Failed close reports Faulted. Drop alone is not a durable async shutdown.

The Host runtime must outlive accepted work and explicit shutdown. Validation
callbacks must be bounded and must not reenter the same writer. Metadata locks
serialize metadata only: a deploying Host must retain independently owned live
key/revocation/authority synchronization through persistence, including after
caller cancellation, or supply a qualified atomic authority-version protocol.
Returning a copied CommerceAdmissionHost from a callback alone does not establish
this synchronization. The integration test uses fixed authority; live external
revocation composition is still open.

* SQLite provider feature

=sqlite= selects [[file:../../crates/mrr-data-backend/src/providers/sqlite.rs][one metadata provider module]]. =mrr-data/backend= exposes the
provider-neutral engine; =mrr-data/backend-sqlite= composes the SQLite feature.
Both are opt-in. The provider uses SQLite WAL with synchronous=FULL, checks the
actual selected mode, and bounds busy waiting to 250 ms. A writer connection
and independent read connection separate historical recovery from a held writer.
BEGIN IMMEDIATE serializes new head/operation decisions across backend instances.
Head and exact completion row are persisted in the same transaction. COMMIT
errors are Unknown, not known no-write. Historical operations are retained.

Opening refuses unknown schema/application identities, foreign nonempty databases,
missing metadata tables and structurally orphaned heads/operations. It does not
recreate lost authority tables as a fresh database. Stored records are bounded
before BLOB allocation and typed decoding. Closing releases connections after
FULL commit barriers; it does not require truncating another live owner's WAL.

The Host must protect the local database directory and choose a supported local
filesystem. SQLite does not authenticate a maliciously replaced database or reject
a restored older valid backup. This implementation therefore supplies physical
local transaction/restart persistence, not cryptographic latest-head authentication,
canonical home enrollment, external payment ownership fencing or power-loss proof.
Immutable block publication remains the existing content-store/provider boundary;
a PublishReceipt needs a truthful durable block ACK from the deploying composition.
The backend currently schedules metadata operations, not the entire blob transfer.

* Executable evidence

[[file:../../crates/mrr-data-backend/tests/integration/backend_consumer.rs][Independent file-backed consumers]] check separate Profiles and namespaces,
exact operation/body conflicts, replay after later head changes, validator refusal,
two independently opened instances racing one head, cancellation with an owned
commit, reserved historical reads, drain/shutdown, input bounds, schema refusal,
lost ACK recovery and refusal to recreate missing metadata tables.

A subprocess exits directly without Rust destructors after a FULL commit; reopening
recovers its receipt/head. Another exits during an uncommitted deletion transaction;
reopening retains the original head and receipt. These exercise actual SQLite
files/WAL and process-exit recovery. They do not simulate power failure, every
filesystem boundary, malicious rollback or multi-host/network filesystems.

The [[file:../../crates/mrr-data-commerce/tests/integration/agentic_ai/commerce/budget_transactions.rs][signed budget consumer]] enrolls a genesis budget through the ordinary
absent-head commit, validates a signed reservation with the shared backend,
closes/reopens, recovers the exact receipt and proves replay skips admission.
No separate Commerce backend was created.

* Remaining performance and lifecycle qualification

One SQLite writer serializes metadata across independent homes. This is a
correctness baseline, not a claimed high-throughput scheduler. Home partitioning,
provider pooling, group flush and integrated immutable publication need matched
measurements before selection. Exposed status reports active writes/recovery,
retained write bytes and completed workers; latency histograms/tenant fairness
and durable retention/GC are not implemented yet. There is no automatic ledger
expiration that could make a reused operation fresh.

Next qualification: matched hot-home/independent-home throughput and p50/p95/p99,
byte saturation and provider stalls, physical fault injection at durable boundaries,
authenticated latest-head/incarnation and live authority-version composition.
Further providers reuse the same engine and conformance consumers; they are
modules/features, not independent backend engines.
