* Source semantics and observable layers

| Source boundary | Actual behavior | Allowed interpretation |
|-----------------+-----------------+------------------------|
| SDK step_inner | StepResult IO/Yield/Sleep become one Io status | Pending can be a driver/lock/yield condition |
| Default Unix PlatformIO | pread/pwrite/pwritev/sync complete in the calling thread | Delegate-call wall is inside poll |
| UnixIO step | No-op | Its elapsed time is not an asynchronous device wait |
| MVCC group park | A waiter can register while another transaction holds the pager commit lock | Waiter latency may depend on another original operation |
| Group unlock/wake | Shared progress releases parked completions | Publisher context can correlate with a different COMMIT |
| Target wake forwarding | Notify original block_on without waiting for observation publication | Detail absence is not a lost commit or permission |

The decorator forwards every IO/File method, including clocks, optional shared
WAL operations, memory IO access, fixed-buffer registration, cancel/drain and
backoff. Only selected synchronous file calls and driver step/wait/drain/backoff
are timed; it does not claim complete kernel-call coverage. Data-path File methods
preserve arguments, buffers, results and completion objects. No new retry,
durability setting, callback placement or authority check is introduced.

An IO scope is confined to the original COMMIT's synchronous worker thread, with
a fixed 256-event limit. Native checks require IO spans inside COMMIT and outside
its Pending gaps, exact operation joins, bounded notifications and a real sync
sample when the wrapper is enabled; disabled probes must emit none. A completion
control checks the original completion finishes and its callback runs once.
Unwinding clears only observation context, never application authority.

Each wake retains a bounded start/end/thread-CPU receipt and publisher's current
scope/operation, if available. Do not mistake execution context for a causal
group identifier. A late publisher can forward before it publishes details;
snapshotting never waits for it. Preserve timestamp/detail publication gaps,
early/unobserved notifications, overlapping forwarding/resumption and overflow.

Delegate-call wall includes the underlying syscall, native completion callbacks,
dispatch and preemption. It is not device-only service time. Synchronous FULL
is the original database setting; this probe does not independently certify
F_FULLFSYNC or physical power-loss persistence. Group sync is charged to its
executing context only. A waiter's overlap with that context's sync is temporal
evidence, not a new durability or causal theorem. Notifications and borrowed
resource return never settle unknown budget or create a final send capability.

The pinned Tokio 1.53.1 Handle.block_on uses BlockingRegionGuard and
CachedParkThread::block_on: poll under a cooperative budget, then park; park
uses a notification state plus mutex/Condvar. This is not a task being requeued
on Tokio's multi-thread task executor. Post-forward delay therefore narrows to
the original thread's park/unpark/OS resumption and immediate loop bookkeeping,
with observation effects retained. Kernel ready-to-run versus mutex reacquire
time remains unmeasured. Low forwarding CPU does not itself prove pure runnable
contention or rule out all scheduling/locking effects.

The off/on ratios change direction across order/round. Host drift and probe
intrusion remain inseparable here; neither an observer speedup nor production
nonregression is established. Do not merge these samples with the old A/AV

* Separate kernel trace refinement

The notification split is an observation boundary, not an I/O attribution rule.
Pre-notification can overlap another operation's synchronous persistence; after
notification the blocked caller still has to reacquire its park mutex and run.
The kernel refinement below separates observed scheduling residence without
claiming a request-correlated device-time decomposition.

A five-second Xcode System Trace attaches only to owned Rust PID 77540 using
the same frozen executable and enabled decorator. The benchmark independently
finishes all 18 cases, 13824 commits and exact recoveries, natural exit, with no
unexpected outcome. This profiled leg is not pooled into the paired campaign.
The trace and all exports remain under /private/tmp/mrr-commit-io-system-*;
its table of contents verifies the attached PID and successful original exit.
The initial sandbox cache-initialization failure and malformed first presentation
conversion are retained separately, not admitted as successful trace analysis.

All 102150 syscall rows resolve to the owned PID. Of 138747 thread-state rows,
130348 resolve to it, 2614 resolve elsewhere and 5785 remain unresolved; only
owned rows participate. Initial zero-time censored state intervals are excluded
from syscall-overlap joins. Do not interpret unavailable typed CPU/wait cells
as zero; this analysis instead joins explicit thread-state intervals by PID,
kernel TID and the same trace clock.

There are 2215 fsync syscalls in this process window. Of these, 1047 have a
recognized COMMIT-function stack (CommitStateMachine or the observer function),
totalling 91.428163 ms: mean 87.324 us, P95 178.500 us, maximum 5.880 ms.
The other 1168 lack that recognized stack; block_on ancestry alone does not
label them COMMIT or setup. Compiler inlining and preparation can affect stack
classification. This is a process-window subset, not 1047 identified timed requests.
